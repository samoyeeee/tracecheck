# 面试问答准备

答案都基于这个项目的真实实现和数据；括号里是可以当场打开给对方看的文件。

---

### 1. 和 LangSmith Engine 有什么区别？

LangSmith Engine 是 LangChain 在 2026 年 5 月公测的托管 agent：它分析生产环境的 trace，从错误、评估器失败、trace 异常和用户负反馈里发现问题，把同类问题聚成 issue，给出修复建议，并生成防回归的数据集和评估器。它面向的是“生产环境里大量真实流量”。

TraceCheck 规模小得多，侧重点不同：

- **结果对不对靠重放，不靠打分。** 在 τ²-bench 这种有可重放环境和标准答案的场景，我直接重放数据库、逐字段对比，和官方判定 449/449 一致（`results/eval_verify.json`）。这在没有标准答案的生产环境里做不到，所以这既是优势也是适用范围的限制。
- **修复是否有效有统计依据。** 版本对比用事先登记的检验和“同版本重跑”的噪声基线（`results/regression_plan.json`）。例如 v2 成功率 34.4% → 30.9%，看着像变差，但在噪声范围内，结论是“需要再查”，而不是直接回滚。
- **我测了自己工具的准确率，包括它不准的地方**（见第 3、6 题）。

一句话：Engine 是“生产环境里的问题发现与闭环”，TraceCheck 是“在可重放环境里，把一次失败变成可验证的结论和回归测试”的原型。

### 2. 为什么这里用 Agent，而不是固定流程？

坦白说，大部分是固定流程，这是有意的选择：
- 规则检查和数据库核验是确定性程序：数据库字段对不对是事实，用程序又准又便宜。
- 只有“读懂一段对话，判断哪一步是根源”这件事程序做不了，才交给模型（调查 agent）。
- 调查环节没有做成“自己循环调用工具”的 agent。原因是免费档每分钟只有 15 次请求，所以先把规则和核验结果跑完，一次性放进 prompt。

如果有更多预算，我会让调查 agent 按需调用工具（比如查某一步的数据库状态）。但我不会为了“看起来像 Agent”而加：这个项目里最可靠的结论都来自确定性部分。

### 3. AI 评委 / 调查 agent 判错了怎么办？

三道防线：
1. **证据必须可查。** 调查 agent 引用的原文由程序逐字核对，找不到就不算证据（`triage/investigator.py` 的 `check_evidence`）。
2. **拿不准就弃权。** 它自报的置信度没用——调参时答错的案例也常报 0.9–1.0（`results/iteration_log.md`）——所以改成 3 次独立采样必须完全一致才作答。测试集上弃权 6/20，作答的 14 条里关键步骤差 1 步以内 11/14。
3. **人工复核台。** 每个 AI 判断都可以确认、修改或驳回，记录写入 `results/human_review.jsonl`，可以用来校准。

我还测了它的稳定性：同一批记录重跑，两次都作答的 18 条，结论 18/18 一致；不稳定的是“作答还是弃权”这个边界（32/47 一致）。

**判错的真实例子：** 类别判断只对 5/14。我做了对照表（`results/category_confusion.json`），发现主要不是随机出错：一是选了另一个步骤（6 条），二是在“该怪用户还是怪 Agent”上和人工标注习惯不同（4 条标注为用户信息不足的，模型都判成 Agent 未遵循流程）。

### 4. Agent 输出有随机性，怎么判断修复真的有效？

1. **先量噪声。** 同一个 v1 重跑一遍，成功率就从 34.4% 变成 33.1%。所有对比都和这个“v1 对 v1”的波动比。
2. **检验方法事先登记。** 跑之前把要比较的指标、检验方法、显著性门槛提交到 git（`results/regression_plan.json`），跑完不改，避免看到结果再挑对自己有利的指标。
3. **按任务配对检验。** 同一个任务在两个版本上各跑 4 次，用配对的符号翻转置换检验，Holm 校正多重比较。
4. **用已知 bug 验证检验本身有没有用。** 第一轮 4 个提示词 bug 一个都没检出。我没有改阈值让结果好看，而是事后分析：3 个 bug 本身没让 Agent 变差（没检出是对的），1 个确实变差但被漏检，原因是同时检验 20 个指标、校正太严（`results/bug_effect.json`）。补实验改成每个 bug 只检验一个事先指定的指标，2/2 检出。
5. **单条失败的重放不能证明修复。** 回归用例重放一次只说明那一次的结果，界面上明确写“次数太少，不能说明修复已被充分验证”。

### 5. 你做了哪些取舍、砍掉了什么、为什么？

- **预算为 0**：全部用免费模型，所以每个阶段都先估算调用次数和天数再缩减规模；调查 agent 不做多轮工具调用。
- **只做一个场景**（τ²-bench retail）：先把一个场景的评测做扎实，而不是浅浅覆盖多个。
- **NL 评委换成免费模型**：成功率因此不能和官方榜单直接比较，这一点在报告里写明了。
- **没做多 Agent、没做自主修复**：最可靠的价值来自确定性核验和统计检验，加 Agent 不会让结论更可信。
- **停用了自己的“假成功”指标**：这是最大的一次取舍，见下一题。

### 6.（很可能被问）你的项目里最大的失败是什么？

“假成功”检测。最初我把“Agent 说办好了、但结果和标准答案不一致”定义为假成功，v1 的失败里有 82 次。

我事先抽了 20 条做人工核验。另一个 AI 读原始记录后建议：只有约 1 条是真的说谎，大部分是 Agent 照模拟用户确认的要求做了、如实汇报了，只是和任务标准答案不同。我据此重新定义（说法和实际执行矛盾才算），但新规则是看过这 20 条才设计的，所以又抽了一组没参与设计的 12 条，我自己逐条判断：只有 1 条对。

我的处理：不再用“发现了多少假成功”这个说法；把指标拆成“说法是否属实”和“结果是否达成任务”；后者在回归测试里是有用的信号（检出了代码 bug），前者在这个数据集里本来就极少见、我的关键词方法也不可靠。这些都写进了报告。

这件事让我学到的是：**先确认指标在测什么，再相信它的数字。**

### 7. 其他可能被问到的

- **数据怎么保证真实？** 每个数字都能从 `results/` 里的文件复现；没跑的写“未测”；AI 给的建议标签单独存放（`results/ai_assisted_review/`），不算人工标注。
- **为什么 v2 修复反而没变好？** v2 加的三条指令针对的是调查 agent 发现的高频问题，但总成功率变化在噪声内；按类型看只有“退货”一类的下降超出噪声，而且同时比较了 8 种类型，可能是碰巧。结论是“需要再查”，下一步应该看退货类的具体轨迹。
- **怎么防止拿测试集调参？** 调查 agent：调参集 9 条、测试集 20 条，测试集只在最后跑。假成功规则：设计用样本 A，测量用从没看过的样本 B。
- **用户是谁、怎么验证需求？** 目标用户是做 Agent 的工程师和 PM。用户访谈：**待补（作者完成 3 次访谈后填写）**。
