# TraceCheck：Agent 失败诊断与回归验证

> 本报告里的每个数字都来自仓库里的结果文件，括号里注明了来源。没有测过的写“未测”。
> 测试环境：τ²-bench retail（114 个任务），被测客服 agent：`glm-4.5-flash`，用户模拟器：`glm-4-flash-250414`，
> 评委：`gemini-3.1-flash-lite`，调查 agent：`gemini-3.5-flash-lite`。全部使用免费档，实际花费 $0.00
> （`results/cost_log.csv`，共 47,955 次模型调用）。

---

## 1. 问题背景

做 Agent 的团队手里不缺运行日志，缺的是**从大量失败里得到可信结论**的办法：

- 一次失败到底错在哪一步？是 Agent 的错、用户的错，还是任务本身有歧义？
- Agent 说“已经办好了”，数据库里是不是真的办好了？
- 改完 prompt 或代码后，新版本是真的变好了，还是只是这次运气好？

TraceCheck 想回答这三个问题，并且每个回答都要能追溯到证据。

> **待补（作者完成）：3 次用户访谈。** 访谈对象：做过 Agent 的同学 / 同事 / 开发者。问题：平时 Agent 出错怎么排查？
> 最花时间的是哪一步？改完 prompt 怎么确认没改坏别的？访谈记录放在这里，作为问题背景的一手证据。

## 2. 系统是怎么工作的

```
一次运行记录 (τ² 格式)
   │
   ├─① 规则检查      确定性程序：工具报错、违反政策（未验证身份、写库前未确认……）
   ├─② 数据库核验    重放 τ² 环境，逐字段对比“运行结束时的数据库”和“标准答案的数据库”
   │                 再把 Agent 的“已办好”说法和它实际执行的写操作对照
   ├─③ 调查 agent    读完整条记录，给出关键失败步骤、类别、原文证据和因果链；
   │                 3 次独立采样必须完全一致、证据必须逐字可查，否则弃权
   └─④ 人工复核      在复核台上确认 / 修改 / 驳回 AI 的判断，写入 results/human_review.jsonl
                     ↓
   回归：把一次失败存成回归用例 → 选一个 Agent 版本真实重放 → 重新核验数据库
```

界面（`web/`）：复核台（诊断报告 + 判断栏）、案例库、评测总览、回归对比、人工核验。
- 只读展示版：https://huggingface.co/spaces/ray12138888/tracecheck
- 能导入记录的在线版：https://tracecheck-uf75.onrender.com （每人每天 3 次 AI 诊断，全站每天 40 次）

## 3. 设计取舍

**为什么前两层用规则和程序，而不是全部交给大模型？**
“数据库里这个字段对不对”是确定的事实，用程序比用模型又准又便宜。我们重放出的数据库结论和 τ² 官方判定 449/449 一致
（`results/eval_verify.json` → `replay_sanity_check`）。模型只用在程序做不了的地方：读懂对话、判断哪一步是根源。

**为什么允许调查 agent 弃权？**
调查 agent 自己报的置信度没有用：调参时，答错的案例它也常报 0.9–1.0（`results/iteration_log.md`）。
于是改成“3 次独立采样，必须完全一致、且关键步骤上能找到逐字原文，才作答”。宁可交给人，也不要自信地答错。
代价是弃权多：测试集 20 条里弃权 6 条（v3 prompt）、13 条（v4 prompt）。

**为什么要做噪声基线？**
同一个 Agent 重跑一遍，成功率本身就会波动：v1 自己重跑，114 个任务的成功率从 34.4% 变成 33.1%
（`results/eval_regression.json`）。不先量出这个波动，就无法判断“新版本变好了”是真的还是运气。
所以每个对比都同时给出“v1 对 v1”的噪声区间，并且检验方法都在运行前提交（`results/regression_plan*.json`）。

**为什么界面上把信息分成三类？**
“已观察到的事实”（程序得出）、“AI 推断”（可能出错）、“仍需核实”分开显示，避免把模型猜测当成事实。

**砍掉了什么：** 没做多 Agent 架构，没让调查 agent 自己循环调用工具（免费档每分钟只有 15 次请求，
所以规则和核验结果先跑完、一次性写进 prompt）。只覆盖 τ²-bench retail 一个场景。

## 4. 评测方法与结果

### 4.1 被测 Agent 的基线（背景，不是 TraceCheck 的成绩）
114 任务 × 4 次 = 456 次运行。pass^1 = **34.4%**，pass^4 = **15.8%**；失败 299 次，其中 274 次数据库与标准答案不一致，
18 次数据库正确但回复不达标，7 次被终止（`results/baseline_v1.json`）。

### 4.2 第 ①② 层：规则检查与数据库核验

| 指标 | 结果 | 说明 |
|---|---|---|
| 数据库重放与 τ² 一致 | **449/449** | 确认核验本身没算错 |
| 失败里报出至少一个问题 | **281/299（94.0%）** | 绝大部分来自数据库对比（274 条）：能说清“哪个字段错了”，说不清“错在哪一步” |
| 成功运行被误报 | **1/157（0.6%）** | |
| 能定位到具体步骤 | **21/299（7.0%）** | 按当前规则；旧规则下是 137/299，但那些大多来自后面被证明不可靠的假成功规则 |

来源：`results/eval_verify.json`、`results/eval_verify_rule1.json`。

### 4.3 “假成功”检测：一个被人工核验推翻的指标

最初的定义（规则 v1）：τ² 判失败，且 Agent 对用户说“办好了”，但数据库结果和标准答案不一致。按这个定义，v1 的 299 次失败里有 82 次“假成功”。

**核验过程：**
1. 按固定种子随机抽 20 条（样本 A），另加 1 条作者指定的案例（`results/false_success_review.json`）。
2. 另一个 AI 助手读原始记录给出建议标签：20 条里只有 1 条是真的假成功，18 条误报，1 条说不清
   （`results/ai_assisted_review/`；**这是 AI 建议，不是人工标注**）。误报的主要原因：Agent 照模拟用户确认的要求做了、
   也如实汇报了，只是和任务的标准答案不同（模拟用户偏离任务、用户中途改主意）。
3. 据此重新定义（规则 v3）：**假成功 = Agent 的说法和它自己实际执行的操作矛盾**；照用户要求做了但不是任务要的，
   单独归为“做了，但不是任务要的”。v1 的假成功从 82 降到 14。
4. 因为 v3 是看过样本 A 后设计的，又按 v3 抽了一组**没参与任何设计**的样本 B（12 条），由作者逐条人工判断。

**结果：规则 v3 的人工核验准确率 = 1/12（8.3%）**（`results/false_success_precision.json`）。
唯一判对的是“说了但根本没执行”的一条（声称改了地址、办了换货，此前没有任何写操作）。
其余 11 条误报的原因相同：规则把消息里的“订单商品清单”和“下一步计划”也当成了“声称已办完”。
规则没有在看过样本 B 后再改，所以这个 8% 是诚实的测量。

**结论：** 用关键词判断“Agent 是否谎称完成”，在这个数据集上不可靠；而真正的谎称完成本来就很少见。
可靠的是另一个信号：“声称完成，但结果与任务不符”——它不等于说谎，但正是它在回归测试里检出了代码 bug（见 4.5）。
报告和简历里因此**不使用“发现 N 个假成功”的说法**。

规则的每一版结果都保留着：`results/triage_rule1/`、`triage_rule2/`、`triage/`（当前）。

### 4.4 第 ③ 层：调查 agent

标准答案：AgentRx 对 τ-bench retail 失败轨迹的人工标注（关键失败步骤 + 类别），按种子 7 分成调参集 9 条、测试集 20 条，
测试集只在最后跑（`results/eval_investigator.json`）。三组对照：

| 组 | 输入 | 步骤完全对 | 差 1 步以内 | 类别对 | 步骤和类别都对 | 弃权 |
|---|---|---|---|---|---|---|
| A | 只给对话 | 7/20 | 10/20 | 6/20 | 2/20 | 0/20 |
| B | + 规则和核验结果 | 9/20 | 14/20 | 6/20 | 5/20 | 0/20 |
| C | + 必须引用原文、不一致就弃权（v3） | 8/20 | 11/20 | 5/20 | 5/20 | 6/20 |
| v4 | C + 因果链和中文说明（网页用） | 5/20 | 6/20 | 3/20 | 3/20 | 13/20 |

- C 组作答的 14 条里，关键步骤差 1 步以内 **11/14**，类别对 **5/14**。各组之间差 1–2 条，在 20 条样本的噪声范围内，不能说哪组显著更好。
- **类别为什么对不上**（`results/category_confusion.json`）：两边用的是同一套 AgentRx 分类，不是体系对不上。
  C 组作答但类别错的 9 条里，6 条是选了另一个步骤，3 条是步骤对、类别叫法不同。最常见的分歧：标注认为是
  “用户信息不足”的 4 条，模型都判成“Agent 未遵循流程”——两边对“该怪谁”的边界理解不同。
- **稳定性**：同一批 v1 失败让调查 agent 重跑一次，两次都作答的 18 条里，步骤和类别 **18/18** 一致；
  但“作答还是弃权”只有 **32/47** 一致（`results/diagnoses/stability_v1.json`）。作答时稳定，不稳定的是弃权边界。
- 案例库 74 条（v4 prompt），调查 agent 作答 22 条、弃权 52 条（`web/app/public/data/reports/index.json`）。

### 4.5 回归检测：埋已知 bug，看能不能发现

检验方法在运行前提交：配对符号翻转置换检验（按任务配对，20,000 次），Holm 校正，α = 0.05。

| 埋的 bug | 怎么埋 | 检验指标 v1 → bug 版 | 校正后 p | 检出 |
|---|---|---|---|---|
| 删“先验证身份” | 改提示词 | 对应规则触发 1.3% → 20.0% | 1.0 | 否 |
| 改模糊“转人工”说明 | 改提示词 | 27.5% → 32.5% | 1.0 | 否 |
| 删“写库前确认” | 改提示词 | 13.8% → 20.0% | 1.0 | 否 |
| 写错参数说明 | 改提示词 | 31.3% → 28.8% | 1.0 | 否 |
| 清空地址第二行 | 改工具调用代码 | 声称完成但结果不符 28.8% → 61.3% | **0.0014** | **是，并定位到字段** |
| 漏掉最后一件商品 | 改工具调用代码 | 26.3% → 53.8% | **0.0065** | **是，并定位到字段** |

同一版本重跑（v1 对 v1）的误报：**0**。来源：`results/eval_regression.json`、`results/eval_regression_4b.json`。

**第一轮 0/4，到底是谁的问题？**（事后分析，`results/bug_effect.json`）在每个 bug 自己的 20 个任务上，看 τ² 成功率的下降
是否超出 v1 自身的噪声区间：

- 删“先验证身份”：41.3% → 31.3%（−10.0，噪声区间 ±8.7）——**Agent 确实变差了，TraceCheck 漏检**。原因：第一轮每次比较同时检验 20 个指标，校正太严。
- 其余三个提示词 bug：成功率变化都在噪声内——**bug 本身没起作用**，没检出是对的。事后核对也显示其中两个几乎没改变 Agent 行为（`results/bug_mechanism_check.json`）。
- 补实验改为只检验一个事先指定的指标，并改用一定生效的代码级 bug。

**注意：** 补实验检验的指标是规则 v1 的“声称完成但结果与任务不符”。按后来的规则 v3（说法与执行矛盾）重算，
两个代码 bug 都不显著（校正后 p = 0.07，`results/eval_regression_4b_rule3.json`），因为 v3 只核对商品、不核对地址内容。
事先登记的 2/2 结论不变，但它测的是“结果不符”，不是“说谎”。

### 4.6 v1 vs v2：修复版能不能上线

v2 在 v1 的指令上加了三条规则（自己查订单、记住每个请求、少转人工）。总成功率 34.4% → 30.9%，校正后 p = 1.0，不显著。
按事先定好的规则，发布建议是 **“需要再查”**（`results/eval_regression.json`）。
按任务类型看（事后分析，`results/regression_by_type.json`）：只有“退货”一类的 pass^1 下降（25.8% → 17.7%）超出了 v1 自身的噪声区间（±7.3）；
同时比较了 8 种类型，这一条可能是碰巧越界，只能当线索。

### 4.7 从单条失败到真实回归

把一次失败存成回归用例（任务、初始数据库哈希、要核对的字段、失败证据、出错版本），选版本真实重放，重新核验数据库。
每次重放前都会核对初始数据库哈希，不一致就停止、不调用模型。

演示（`results/regression_cases/rc_bug_dropitem__task_2__trial_1.json`）：

| 重放版本 | 用例字段（退货商品、退款方式、订单状态） | 整个任务（τ²） | 模型调用 | 用时 |
|---|---|---|---|---|
| v1（没有这个 bug） | 全部正确，3 件都退了 | 未通过：回复里 T 恤数量不对 | 28 | 159 秒 |
| bug_dropitem（原来出错的版本） | 不对：这次一件都没退，直接转了人工 | 未通过 | 11 | 74 秒 |

各重放一次只说明这一次发生了什么，不能说明修复已被充分验证，界面上也这样写。

## 5. 典型失败案例

1. **少退一件，但如实告知（bug_dropitem 任务 2 第 1 次）**：确认要退 3 件，第 28 步只提交了 2 件（代码 bug 漏掉了手表），
   补交被拒，Agent 在第 30、32 步告诉用户手表没退成。旧规则判成“假成功”，这是误判；修正后不再算。
   调查 agent 3 次一致定位到第 28 步。这条后来做成了回归用例。
2. **真正的谎称完成（v1 任务 78 第 3 次，样本 B4）**：Agent 在第 14 步说“已把地址改好”，第 20 步说“换货已办”，
   此前没有任何写数据库的操作。这是唯一被人工确认的假成功。
3. **照用户说的做了，但不是任务要的（v1 任务 7 第 0 次）**：任务设定“客服问确认时只换台灯”，但模拟用户明确确认换水瓶和台灯两样，
   Agent 照做并如实汇报。τ² 判失败，旧规则判“假成功”；实际是模拟用户偏离了任务。
4. **计划顺序错误（v1 任务 112 第 1 次，作者人工备注）**：用户要改笔记本订单的地址、换笔记本型号、换手表表盘。
   Agent 第 28 步先改了笔记本订单的商品（按政策，改过商品的订单不能再修改），地址最终没有改；手表其实在另一张
   待发货订单 #W9810810 里，Agent 却以“系统限制”为由没改，最后转人工。被标出的“笔记本已改好”属实，
   问题在于操作顺序和没找对订单，不在于说谎。
5. **超范围执行（v1 任务 99 第 0 次，作者人工备注）**：任务只要取消滑板，Agent 在第 26 步取消了整张订单 #W8855135
   （里面还有空气净化器、登山鞋、瑜伽垫）。

## 6. 局限性

- **只测了 τ²-bench retail 一个场景**，被测 Agent 只有一个模型（`glm-4.5-flash`）。
- **样本量小**：调查 agent 的测试集只有 AgentRx 的 20 条；样本 B 只有 12 条；每个 bug 版本只跑了 20 个任务 × 4 次。
- **“假成功”检测不可靠**：人工核验准确率 1/12，见 4.3。用关键词理解 Agent 的话是这套系统最弱的一环。
- **定位到具体步骤的能力有限**：确定性部分只能对 21/299 次失败指出具体步骤，其余依赖调查 agent，而调查 agent 经常弃权。
- **NL 评委不是官方的**：τ² 默认评委是 gpt-5.4-mini，这里换成了免费的 `gemini-3.1-flash-lite`，成功率不能和官方榜单直接比较。
- **用户模拟器会偏离任务**：很多“失败”其实是模拟用户没按任务设定说话。
- **一部分分析是事后做的**（按类型的噪声区间、bug 是否生效、类别对照），文中都已标明，不能当作事先登记的结论。
- **用户访谈尚未完成**（见第 1 节）。

## 7. 和同类工具的区别

| | TraceCheck | LangSmith Engine | Langfuse | AgentRx |
|---|---|---|---|---|
| 是什么 | 个人项目：针对 τ²-bench 的失败诊断 + 回归验证 | LangChain 的托管 agent，分析生产 trace（2026 年 5 月公测） | 开源的 LLM 观测与评测平台（MIT） | 微软研究院的开源诊断框架和基准（MIT） |
| 找失败 | 规则 + 数据库重放 + 调查 agent | 从错误、评估器失败、trace 异常、用户负反馈中发现，并把同类问题聚成一个 issue | tracing + LLM 评委打分 + 人工标注队列 | 由工具 schema 和政策生成约束、逐步检查，再由 LLM 评委判关键失败步骤和类别 |
| 结果对不对 | **重放环境、逐字段对比数据库**（需要有可重放的环境和标准答案） | 依赖评估器和 trace 信号 | 依赖评估器 | 依赖约束检查和 LLM 评委 |
| 修复与回归 | 失败 → 回归用例 → 真实重放 → 重新核验；版本对比带噪声基线和事先登记的检验 | 提出修复建议、生成数据集样例和防回归评估器，可推送到 Linear | 数据集 + 实验，可在 CI 中运行 | 不涉及 |
| 不确定时 | 弃权，交给人工复核；人工结果写入文件 | — | 人工标注队列 | — |

TraceCheck 不是要替代这些平台。它想展示的是：在**有可重放环境**的场景里，先用确定性核验确定“结果对不对”，
再让模型在严格约束下回答“错在哪一步”，并用噪声基线和事先登记的检验判断“修复是否真的有效”。
它借用了 AgentRx 的失败分类和人工标注作为调查 agent 的评测标准。
